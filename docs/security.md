# Security & Privacy

We hold other companies' Trello and Jira tokens, access to their Crisp conversations, and optionally their OpenAI keys. A leak would end the product, so this is a top requirement. Because the code is public, the security design must work without any secret code.

## Credentials
- Encrypted at rest with **AES-256-GCM envelope encryption** (`packages/crypto`): a random data key for each record, wrapped by a master key.
- Master key: an env var (generated by the self-host setup script). Rotation is supported by storing a key version with each record.
- Decrypted only inside the worker or server route that needs them. They never go to the browser; the UI shows `••••1234`.
- Never logged. pino redacts `authorization`, `token`, `apiKey`, `secret`, `password` fields.
- Disconnecting deletes the credentials and revokes the token where possible.
- Platform secrets (Crisp plugin token, Trello app key/secret, Atlassian OAuth client secret, billing keys) live only in env vars, never in the repo. Secret scanning runs in CI.

## Crisp linking
- A Crisp `websiteId` can be linked to **only one** workspace (UNIQUE constraint).
- Linking happens only through the Crisp plugin settings page flow, which proves the user controls that Crisp website. A user can never type in a website ID. (The exact proof method is checked in Phase 0.)

## OAuth
- Request the minimum scopes. Use the `state` parameter (CSRF protection), and PKCE where supported.
- Refresh tokens are stored encrypted. If a refresh fails → connection `revoked`.

## Webhooks
- Verify every incoming signature: Crisp plugin hooks (`X-Crisp-Signature`, HMAC-SHA256) and billing provider webhooks. Reject invalid ones with 401.
- Reject Crisp hooks whose timestamp is too old (replay protection).

## Platform admin
- `/api/admin/*` and `/admin` are only for signed-in users whose email is in `PLATFORM_ADMIN_EMAILS` **and** who have 2FA enabled. Everyone else gets 404 (not 403), so the routes aren't advertised.
- Every write is logged in `admin_audit_log` (who, what, before/after).
- Admins can't read customers' decrypted credentials or OpenAI keys through any route.

## Tenant isolation
- Every table carries `org_id` (directly or through its parent), and every query filters by it. Integration tests try cross-workspace access.
- Roles: owner (billing), admin (connections and automations), member (read + review queue).

## Customer data (PII)
- Customer names appear in tickets only if `includeCustomerNames` is on (off by default).
- Emails and phone numbers are stripped from generated ticket text.
- The conversation link appears only if `includeSourceLink` is on.
- Transcripts are sent to OpenAI. This is disclosed in the privacy policy, and API data isn't used for training.
- Retention limits: see [data-model.md](data-model.md#retention).

## AI-specific
- Prompt injection: customer text is marked as untrusted, output is limited by a strict schema, the rubric sets priority, and `issueId`s are checked against the ones we supplied.

## Before launch
- Privacy policy, terms, a DPA template and a security page.
- Dependency scanning and secret scanning in CI.
- An audit log for connection and automation changes.
- A `SECURITY.md` in the repo explaining how to report vulnerabilities.
