## Context

Customers send bugs, UI complaints, and feature requests through Featurebase (Messenger chats + feedback-board posts). Today someone must read each chat and hand-create tickets. This SaaS lets any team sign up, connect Featurebase (source) and Trello and/or Jira (destinations), pay, and switch on an automation that:
- Uses AI to decide if a chat/post needs **code change** (bug, UI/UX, feature, improvement, performance, infra/deploy, security, data). How-tos, account questions, greetings, and issues resolved in chat → no ticket.
- Creates a ticket with type, priority 1–5, clean title/description, repro steps, attachments, and a due date **only if the customer explicitly stated one**.
- Keeps the ticket in sync as the chat continues (updates/comments), supports multiple tickets per chat, and merges duplicates across customers into one ticket.
- Fans out to every connected destination (Trello + Jira both get the same ticket). Routing rules are future work.

Greenfield: `/Users/kartik/Code/Dev task automation` is empty. Starts as a personal/portfolio project, built to launch as a real SaaS. No deadline.

## Key decisions

- **Stack:** TypeScript monorepo (pnpm + Turborepo). Next.js (dashboard, API routes, webhooks, OAuth callbacks), separate Node worker with **BullMQ + Redis**, **Postgres + pgvector**, Drizzle ORM, zod, Better Auth (orgs plugin), pino + Sentry. Host everything on Railway initially.
- **AI:** OpenAI (vision for screenshots, strict JSON structured outputs, embeddings). Small model by default, escalate to a stronger model for long/ambiguous threads; model names in config. Provider interface so DeepSeek (text-only fallback) or others can plug in. Platform pays AI cost; tokens/cost tracked per org.
- **Auth to tools:** Featurebase = API key. Trello = authorize-URL token flow ("Connect Trello" button, our app key). Jira Cloud = OAuth 2.0 (3LO), API token + email as fallback. No Jira Server/DC.
- **Billing:** Stripe (test mode for MVP): Checkout, Customer Portal, webhooks. Behind a `billing` package interface; evaluate Paddle/Lemon Squeezy (merchant of record) before public launch. Paywall on enabling an automation.
- **Priority:** 5-level, 5 = highest. 5 Critical/red/Highest · 4 High/orange/High · 3 Medium/yellow/Medium · 2 Low/lime/Low · 1 Lowest/green/Lowest. AI uses a fixed rubric (5 = outage/data loss/security/payments; 4 = core broken, no workaround; 3 = workaround exists or important feature; 2 = minor UI/small improvement; 1 = cosmetic).
- **Due date:** AI returns the exact customer quote (`dueDateQuote`) or null; code resolves it with chrono-node against message timestamp + workspace timezone. No quote → no due date.
- **Attachments:** always copied (stream download from Featurebase → upload to Trello/Jira, nothing stored by us). Fallback to the source URL only if upload fails/too large. Screenshots also sent to the AI (capped count).
- **Automation settings (toggles):** `includeSourceLink` (default off), `includeCustomerNames` (default off → "Reported by N customers"). Also `minConfidence`, `quietWindowSec` (~180), `timezone`, `language` ('en'), sources (conversations/posts).
- **Assumptions:** tickets written in English with original quote preserved; admin replies + internal notes included as AI context; no backfill on enable, but a "dry run on last 10 chats" button; low-confidence items go to a Review queue.

## Pipeline

1. `POST /api/webhooks/featurebase/:connectionId` → verify signature → insert `source_events` (unique provider event id) → 200 → enqueue `thread.evaluate` with jobId = thread (debounced quiet window; immediate on `conversation.admin.closed`).
2. Worker (per-thread lock): fetch full thread + attachments from Featurebase API; load issues already linked to the thread; pgvector top-5 similar open issues in the automation.
3. AI triage → strict JSON → zod validate → actions: `no_action | create | update(issueId) | duplicate_of(issueId)`; multiple actions per thread allowed.
4. Per destination, independently (`ticket.deliver` jobs, idempotent via `destination_tickets` check): create card/issue, ensure labels, priority, due date, upload attachments.
5. Updates: comment "Customer added: …", adjust priority/due date/labels; rewrite description only if remote `updatedAt` == our `last_remote_updated_at`. If resolved in chat → comment "Possibly resolved in chat", never auto-delete.
6. Duplicates: AI-confirmed match → comment + `report_count++` + new attachments (+ names if toggle). Match is closed remotely → create new ticket linking the old one.
7. Write `ai_runs`, `activity_log` (decision + reason shown in dashboard). Long threads keep a `rolling_summary`.

Featurebase webhook topics: `conversation.user.created`, `conversation.user.replied`, `conversation.admin.replied`, `conversation.admin.noted`, `conversation.admin.closed`, `conversation.admin.opened`, `post.created`, comment events. One webhook per Featurebase connection, shared by automations (Featurebase allows 10 per organization by default).

## Data model

`organizations`, `users`, `memberships(role)`, `subscriptions(stripe ids, plan, status, period_end)`, `connections(org, provider, auth_type, credentials_encrypted, metadata, status)`, `automations(org, source_connection, enabled, settings jsonb)`, `automation_destinations(automation, connection, config jsonb: board/list/label ids | project/issue-type map/priority map)`, `source_events(provider_event_id UNIQUE, topic, payload, status)`, `threads(automation, source_type, source_id UNIQUE, state, last_processed_message_id, rolling_summary)`, `issues(thread, title, body_md, type, priority, due_date, due_date_quote, confidence, embedding vector(1536), report_count, status active|pending_review|dismissed)`, `issue_reports(issue, thread, customer_ref)`, `destination_tickets(issue, automation_destination, external_id/key/url, last_remote_updated_at, status)`, `ai_runs(model, tokens, cost, decision, raw_output)`, `activity_log`.

AI output: `actions[] { kind, issueId?, type, title, summary, stepsToReproduce?, expected?, actual?, environment?, priority 1–5, priorityReason, dueDateQuote|null, relevantAttachmentIds[], confidence, reason }`.

## Phases

0. **API spike:** confirm Featurebase webhook create-via-API, conversation/post payloads, thread fetch endpoint, attachment auth; Trello authorize flow; Jira 3LO + createmeta. Output: notes + real payload fixtures.
1. **Foundation:** monorepo, schema/migrations, Better Auth + orgs/invites, crypto package, CI, Sentry.
2. **Connections:** Featurebase (key verify + webhook register), Trello (authorize, board/list picker), Jira (OAuth, site/project/issue types, required-field check). Secrets never sent to the client.
3. **Ingest + queue:** webhook route, signature check, idempotent event store, threads, debounce, per-thread lock, thread fetch.
4. **AI triage:** schema, prompt + rubric, ticket/no-ticket rules, vision, chrono date resolution, eval harness with 60–100 labelled conversations.
5. **Ticket creation:** Trello + Jira destinations, label auto-create, priority mapping, Markdown→ADF, attachments, fan-out, idempotency.
6. **Updates + duplicates:** linked updates/comments, human-edit check, embeddings, duplicate merging, toggles.
7. **Dashboard:** setup wizard, settings, activity log, review queue, dry run, connection health.
8. **Billing:** Stripe products/prices, Checkout, Portal, webhooks, enable-gating, usage limits.
9. **Hardening:** per-connection rate limiting (Trello per token/key, Jira 429 Retry-After), backoff, 401 → pause + email (events kept 7 days), alerts, landing page, docs, privacy policy.

## Edge cases to handle

Duplicate/out-of-order webhooks; concurrent messages (thread lock); vague first message (no_action); mixed how-to + bug (bug only); reopened chats; remote ticket deleted (404 → mark broken, don't recreate); revoked tokens; rate limits; partial fan-out failure (per-destination retries/status); Jira required custom fields (block at setup); oversize attachments; long threads (rolling summary); prompt injection (transcript as data, rubric + schema bound output); PII (names off by default, strip emails); subscription lapse / usage cap (pause); fuzzy dates like "ASAP" (no due date, may raise priority); non-English input.

## Verification

- **Unit:** date resolver ("by Friday" sent on Saturday, "end of month", timezones), priority/type mapping, Markdown→ADF, encryption round trip, webhook signature valid/tampered, schema rejection of bad AI output.
- **AI evals** (run on every prompt change): ≥90% ticket-vs-no-ticket accuracy, ≥85% type, ≥85% priority within ±1, **0 hallucinated due dates**.
- **Integration:** connectors against recorded HTTP (msw/nock) + nightly against real sandboxes (Trello test board, free Jira Cloud site, Featurebase test workspace).
- **Pipeline scenarios:** same webhook ×3 → 1 ticket; 5 rapid messages → 1 evaluation; follow-up → comment not new ticket; second customer same bug → duplicate comment, report_count = 2; Jira down → Trello card + Jira retries then succeeds.
- **Billing:** Stripe CLI test events (checkout completed, payment failed → pause, cancelled).
- **E2E (Playwright):** sign up → connect all 3 → configure → pay with test card → enable → send a real Featurebase chat → card in Trello + issue in Jira with labels, priority, files; visible in activity log.
- **Negative:** bad Featurebase key, revoked Trello token, Jira project with required field, non-admin attempting billing changes.

## Acceptance criteria

New user can self-serve signup → connect → configure → pay → enable. Bug chat → Trello card and Jira issue with correct type, 1–5 priority (colour/Jira priority), repro steps, attachments. Due date only when explicitly stated. "Hi"/how-to → no ticket with reason logged. Follow-ups update the linked ticket. Same bug from another customer → comment + count. Toggles change ticket content. No duplicate tickets from duplicate webhooks. Revoked access pauses cleanly without losing events (7 days). Unpaid org can't enable. Eval targets met.
